## 0. 为什么要拆

这条线的起点只是「给积压加一个只读查看命令」——因为 status 只报一个数字
（"待发布答复 13 条"），"要不要清掉"这个决定没法做：抑制不可逆，而人手上只有一个数。
**看不见的东西没法授权。**

做着做着它牵动了抑制核心、发布路径、锁语义、登记表校验。评审连着八轮，每轮都能找出
新的 P1，而其中相当一部分是**上一轮修法自己引入的**。评审的判断是：

> 应该拆，而且**不要按现有提交机械 cherry-pick**——这些提交已经混合多个责任。
> 建议保留当前分支作为集成基准，从 `main` 重建堆叠。

拆分的意义不是"分批交付"，而是**让每一块能被真正审完**：一个 PR 装了六件事，
审的人每次只能抓到一层。

但抑制事务的核心保证——"摘要核对过的那份字节就是写回去的那份"——**只有在所有写方
共用同一把锁时才成立**：评审用探针在"快照读完、写回之前"改掉同一条记录，

**第二次范围调整（评审指出）**：统一写锁给资格提升新增了一个**可达的永久卡住状态** ——
提升只重试约 720ms，而竞争方持锁做真实网络发布默认可达 12 秒。watcher 只记一个
`eligibility_pending` 就退出，没人消费的话那条答复再没有任何路径获得资格。
"留了状态没人管等于没留"，所以**恢复消费者也移进第 3 层**，第 3 层才能独立安装。

恢复消费者一旦前移，原计划留在第 5 层的**恢复标记验真**也必须跟着前移 ——
它决定"给哪条记录发资格"，就是发布授权制品。评审构造过：标记 `claim_key` 与文件名
自洽、但 `event_key` 指向别人的答复，于是这张标记替另一条 claim 拿到了发布资格。
所以事件键按 thread + 文件名里的 claim key **自己算**，命中记录还要 `run_id === claim_key`、
必须唯一。

**第 3 层完成恢复标记验真**（封闭键集**连同取值域**、事件键自己算、
命中唯一且 run_id 对得上；标记缺席时在锁下按当前 event/run 复核，
排除"另一个恢复器先做完了"这种歧义）。

## 2. 第 3 层：抑制事务

分支：`fix/outbox-suppression-transaction`

这一层最危险，因为它是**不可逆写入**：被停下的内容不会再发出去，
也不会因为重新绑定或轮转话题而回来。

### 2.1 要做的

- **共享抑制核心**：判据两侧共用一份；无条件写原语（`suppressRecords`）
  **收回私有**，外面唯一能走的路是守卫事务。
  理由：守卫写在调用方那一侧，永远是"记得调的人才受约束"。
- **跨进程摘要**：预览打印、`--apply` 原样带回。绑**整个文件的字节**，不手挑字段。
  理由：手挑字段的错误模式是"想不到的那个字段"，补一个还有下一个
  （曾经漏掉 `publish_eligible_at`，改它之后摘要一字未变）。
- **代际锁**：有旧格式记录时跟轮转串行；**锁内按稳定身份重新定位**再算。
  理由："锁内重读"曾经只做了接口没做实现 —— 闭包了锁外那份，等于只是拿了一把锁。
- **原子性**：锁内只读一次盘，摘要核对与写回用同一份字节。
  同一条记录的所有语义修改共用同一把锁。
- **两侧显式抑制 CLI**：Claude 侧 `feishu-suppress-outbox.mjs`、
  Codex 侧 `codex/suppress-outbox.mjs`。**预览与执行必须给出同一个结论。**
- **单快照**：预览的渲染、摘要、锁内的核对与写回全消费同一次读盘。
  理由：读两遍时评审在两次读之间做同名替换 —— **人看到 A，摘要绑的是 B**，
  他"合法地"永久抑制了一条自己从没看过的记录。摘要能防"预览之后变化"，
  防不住"渲染和摘要看的不是同一份"。
- **恢复消费者 + 标记验真**：见上面的第二次范围调整。

### 2.2 要接上的事实链后两段

第 2 层已经钉死前两段，这一层接后两段：

```
auditOutbox → outboxMutationBlocker → 查看器是否给命令
            → 预览 → 锁内重读后的最终闸门
```

### 2.3 已知的坑（都是踩过的）

- 安全性长在展示层等于没有：查看命令不显示处置命令，挡不住人直接跑抑制。
- 只比"待发集合"的 CAS 看不见坏 JSON、已发布、已抑制的文件。
- 预览之后轮转过，只可能**跨进程**发生 —— 在 `--apply` 时现算的值永远自洽。
- 损坏记录整批拒绝：混着抑制会让人以为"那批都处理了"。

## 3. 第 4 层：手工发布计划与目标 CAS

分支：`fix/codex-manual-drain-cas`

### 3.1 要做的

- **发布计划摘要**：不只绑内容，要连**解析后的目标代际和根消息**一起绑。
  理由：旧格式记录的目标靠当前状态现算 —— 预览时目标是 `om_old`，轮转到 `om_new` 后
  **摘要一字未变**，`--apply` 会把内容发去新话题。**人授权的是"发到那个话题"，
  不只是"发这些字"。**
- **严格参数白名单 + 恰好一个 selector**：这个入口会真的发消息。
- **锁内字节快照**：完整性校验、卡片构造、`markSent` 全用同一份。
  只在锁内再 `auditOutbox()` 一次不够 —— 那只是把窗口挪到"审计到构卡"之间。
- **预览打印完整可执行命令**：含脚本路径与 selector，过 `shellQuote`。
  提示指向的操作做不到它说的事，这个坑踩过不止一次。
- **目标解析失败 = 预览就失败**，不打印落盘命令，也不哈希成一个"正常"的计划。

### 3.2 必须补回的一条测试

`drainTaskOutbox` 的 **`atRecheck` 分支现在没有任何测试盯着**。

它在拆分核对时被发现：用全历史并集比对，共 6 条测试"曾经存在、最终不在"，
其中两条没有替代 —— 一条（真 shell 跑生成的命令）已在第 2 层补回，
**这一条留给第 4 层**。

## 4. 第 5 层：自动发布生命周期

分支：`fix/codex-auto-publish-lifecycle`

最难的一层：并发 + 授权真伪，前面在这上面栽过最多次。

### 4.1 要做的

- ~~三个写方共用同一把发布锁~~ —— **已移到第 3 层**（见上面的范围调整）。
  这一层只需保证发布本身也在同一把锁内。
- ~~eligibility_pending 要有消费者~~ —— **已移到第 3 层**（同上）。
  连同它必需的标记验真一起。
- ~~锁的失败要有人接住~~ —— **已在第 3 层实现**（跟恢复消费者一起前移）。
  watcher 现在会落标记、在同一个截止时间内扫到有结论，并照实说原因。
- **自动发布的授权凭据要验真。**

  **先说清现状，别把计划写成现有物**：今天并**不存在**一个"run 完成 marker"。
  资格是 watcher 在 run 终局确认后直接写 `publish_eligible_at`；
  `claims/<key>.completed.json` 是**发布调用之后**才写的，它是记录不是凭据。
  终局证据是 run 的 `.jsonl` / `.exit.json` / `.last-message.txt`。

  这一层要做的是二选一（先定，再做）：
  - 让 `readCodexRunOutcome` 那套终局证据本身成为受验的凭据；
  - 或者**新增**一个显式的 run 完成 marker，并按下面这套验真。

  验真要求（跟第 3 层恢复标记那份相同，实现可照抄）：封闭 schema **连同取值域**、
  文件名与 `claim_key` 一致且是真实 key 形状、规范时间、`run_state=completed`、
  **`event_key` 由 task/thread/claim 推导得出（不能由凭据自带）**、
  outbox 记录的 `run_id === claim_key` 且命中唯一。
  **共用一份要求不等于共用一份校验** —— 两个制品各自都得验。

  **决定（2026-08-27，评审定）：选 (a)。**理由：`.jsonl` / `.last-message.txt`
  由 Codex CLI 写、`.exit.json` 由 runner 在子进程退出后写，三者与发放资格的
  watcher 不同源；watcher 自写 marker 是自证，runner 新写 marker 只是把 `.exit.json`
  复制一份。加强 `.exit.json` 的身份绑定不算 (b)：同一写方、同一时点、同一生命周期。
  六条要求在 (a) 下的映射，以及**两处有理由的偏离**：
  - 封闭 schema：**只封 bridge 自有的退出回执**（逐字键集 + 分支取值域）。`.jsonl`
    是上游 Codex CLI 的可演进协议，采用"所消费字段严格、未知扩展兼容" ——
    全键封闭会让 CLI 增加一个无害字段就令发布链停摆。（偏离 ①）
  - 文件名与 key：watcher 入参先验形状；三个路径全部从 runsDir + key 派生，
    回执内 `claim_key` 必须等于文件名 key。**评审第二轮更正**：文件名绑定只证明
    "B 的回执放在 B 的文件名下"，证明不了旁边两份内容是 B 的（保留 B 的合法回执、
    把 A 的 JSONL 与最终输出覆盖到 B 的文件名 → B 的 claim 授权了 A 的答复）。
    所以成功回执再封两份**内容摘要**（`jsonl_sha256` / `last_message_sha256`，
    runner 在原子写回执前算），验真器每份制品只读一次、先核摘要、再从同一份字节
    解析；算不出摘要时 runner 写 `artifacts_unreadable`，永远解释不成完成。
  - 规范时间：只验回执 `recorded_at`；不给 JSONL / last-message 人造时间字段。
  - `run_state=completed`：**改为"验真器推导出的状态为 completed"**（exit 成功分支 +
    observed thread 匹配 + turn.started/completed + 无 turn.failed + 无递归 +
    最终输出非空），不由任何单一写方自报 —— 没有单个写方掌握全部事实，
    允许 runner 自报 completed 反而把复合事实降级成自证。（偏离 ②）
  - `event_key`：凭据里不存它，由可信 task 的 thread 与已验真的 key 推导。
  - `run_id === claim_key` 且唯一：初始 watcher 路径与恢复路径都带 `requireRunId`
    （初始路径此前漏传，本层修）；检查在写入 `publish_eligible_at` 之前。
  "两个制品各自校验"指：**run 终局复合凭据**（三个文件、一份逻辑凭据，由
  `verifyCodexRunCredential` 验）与**恢复标记**（第 3 层契约）。关系是 AND：
  初始提升验前者；恢复提升两者都验；恢复标记的 `run_state=completed` 不能代替
  终局证据；发布后的 `completed.json` 不是这两个制品之一，仍只是结果记录。
- **锁内字节快照**：同第 4 层。
- **授权判据只有一份**：`publish_eligible_at` 只认规范 ISO（`hasPublishAuthorization`）。
  写端已在第 3 层收敛（原来把任意非空字符串判成 `already_eligible`，于是恢复器撤掉
  标记而发布筛选不认，答复再次永久留队 —— 而且唯一的恢复证据被销毁了）。
  **这一层要把发布筛选那侧也收敛过来。**

## 5. 工艺要求（六层通用）

这些不是流程装饰，每一条都是这条线上付过账的：

1. **守卫要长在会被真正调用的那个入口上。**
   曾连续三轮长错地方：长在返回值上（消费方没读）、长在展示层（真入口不走）、
   长在核心里但消费方没接。
2. **判据只留一份。** 一个"共用校验器"只要还有第二份判据在外面，它就不叫共用。
3. **变异验证每条守卫。** 而且要先确认**变异真的落在有效位置** ——
   "变异不红"有两种原因：守卫没生效，或者变异没生效；分不开这两者，
   变异验证本身就会骗人。
4. **测了原语不等于测了真实入口。** 读源码匹配正则更不算。
5. **夹具要像真的。** 夹具比真实数据宽松，等于替被测代码放行一类现实中不存在的输入。
   计划中的独立清理见下节。
6. **不确定的事别写成确定。** 曾两次把没做的事写成做完的：
   注释声称"有一条测试盯着"而那条测试不存在；零引用守卫扫的名字不全却断言"一处都没有"。

### 5.1 语义差分契约

第 2 层引入、建议在 3/4/5 层复用。对每个 mutator 比较修改前后的原始 JSON：

- `ok:false` ⇒ 文件字节完全不变
- `ok:true` ⇒ 修改后仍能被同一读取器接受
- 除**人写出来的**允许清单外，所有路径深度相等
- 应删除的字段确实消失，而不只是新字段出现
- 加停用条目 / 加顶层扩展字段 / 调换数组顺序 → 结果不变
- 注入重复或矛盾身份 → 必须 fail-closed

抑制是不可逆写入，"除允许清单外一律不变"在第 3 层比在登记表更值钱。
