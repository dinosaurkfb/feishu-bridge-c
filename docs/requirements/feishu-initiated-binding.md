## 3. 四个缺口与方案

### G1 枚举本机项目/会话（不破 chat 零工具边界）

chat 回合是零工具的，读不了本机——这是 §6a 拍板保下来的边界，不动它。
方案：**确定性控制命令**（像 `/feishu-mode` 一样路由器当场执行，不经模型）：

- 新命令（暂名）`/feishu-projects`：R0 只读，**owner-only**（清单含本机项目名，
  敏感度高于 status）；路由器跑确定性枚举脚本，结果走同步回执（枚举很快，不需要 deliver）。
- 清单内容拍板项：只列「已装桥的项目」（现有 binding/订阅控制面派生，最小实现）
  还是「本机全部项目 + 活跃会话」（要新的枚举面：Claude 会话存储 / herdr panes，
  信息暴露面大，且跨链语义复杂）。**建议先只列已装桥的项目 + 其活跃工作线**，
  真实需要再扩。
- 清单条目带稳定序号（写进一次性 pending-attach 状态，供 G2 引用）。

### G2 绑定执行（attach——认领既有话题，与现行 bind 建新话题相反方向）

- 新命令（暂名）`/feishu-attach <序号|项目名>`：R3 控制，owner-only，正文封闭形状
  （与 /feishu-mode 同纪律：多一个字不算）。
- 路由器动作：秒级回执「已受理」→ 异步执行 attach：把当前话题的
  {session_id, chat_id, （G4 反查到的根 om_/omt_）} 登记为该项目的 binding
  （复用现行 binding 结构与写事务；registry 由入站路由器维护，与现行职责分工一致）→
  结果经 **deliver** 回报（此刻回合早已结束，正是 G3 的用武之地）。
- 与现行语义的关系：attach 后该话题状态 = active binding，rotate/unbind/mode
  全部照现行规则工作。一个项目已有 active binding 时 attach 第二个话题怎么办
  ——拍板项（拒绝 / 允许并存为会话级 binding / 换绑）。

### G3 deliver = 绑定前出站通道（方向 1，范围收窄）

- **用途限定**：绑定引导流程内的异步回报（attach 结果、失败说明），以及
  （可选拍板）chat 态回合超时后的补答。**不做**权威出站的替代——对比结论
  （topic-quick-bind.md §6）：无消息 ID、无对账、无幂等、纯文本，工程属性不够。
- **纪律**：每条 deliver 必须逐条对应一条 owner 入站消息（非自发）；调用点只在
  入站路由器 attach 流程；测试注入口（假 aily-cli bin）保证套件不打真飞书；
  投递记录进 .runtime-data 回执域供 doctor 对账。
- **授权**：这是新增自动写入类别，按 CLAUDE.md 需要 Frank 单独授权
  （授权对象：「attach 流程内、逐条对应 owner 入站的 deliver 回报」这一条，不是
  deliver 的任意使用）。

### G4 绑定后出站锚定（拿到话题根 om_，让现行出站接管）

入站只有 msg_（Aily 命名空间），反查死路已实测。三个选项：

| 选项 | 做法 | 代价 |
|---|---|---|
| **a. 消息读权限反查（推荐）** | attach 时 bot 用消息读 scope 按 chat_id + 时间窗 + 发送者 + 文本逐字匹配，唯一命中 → 取该消息 om_ / thread 根；不唯一 → 让 owner 再发一条含一次性短码的消息再查（短码只用于反查匹配，非 bearer） | Frank 去开放平台给 bot 加消息读 scope（具体 scope 名装配时以开放平台文档核对，此处不写死）；一次性动作 |
| b. 绑定后出站也走 deliver | 无需新权限 | 纯文本、无对账，长期话题体验/工程双降级 |
| c. attach 时桥建新话题 | 复用现行 bind | 违背「留在原话题」的初衷，体验折损 |

推荐 a：反查只在 attach 时做一次，锚定后与现行话题完全同构；b 作为 scope
未就绪期间的过渡降级。

## 4. 对《四层关系、交互模式与权限分级》的影响

| 层/节 | 变化 |
|---|---|
| 第 3 层状态机 | 新增迁移：未绑定 →（owner `/feishu-attach`）→ 已绑定。绑定的建立方向多了一种：**飞书发起、认领既有话题**（attach），与现行**本地发起、桥建话题**（bind）并列。binding 记录多一种锚定来源（反查的根 om_ + session_id + chat_id） |
| 出站通道 | 从一条变两条：权威出站（bot 消息接口，绑定后）+ 绑定引导回报（deliver，绑定前，G3 范围）。「写飞书」的口子要在文档里列成两个，各带各的纪律 |
| §4 交互模式 | chat 行补一句：chat 态下的控制命令出口是 `/feishu-bind`（建新话题）**或 `/feishu-attach`（认领本话题）**；chat 行状态改「已实现」（现文档 §4/§6 自相矛盾，需订正） |
| §5.4 命令表 | 加两行：`/feishu-projects`（readonly，R0，owner-only，路由器当场执行）、`/feishu-attach <对象>`（model_control 或 router_control——拍板项，R3，owner）。两条均从飞书开放（这正是「飞书发起」的意义），终端不需要（终端有更全的 bind） |
| §5.3 交叉表 | 结构不变；chat 行 R3 格子今天就是 owner，attach 落进既有格子 |
| 第 2 层 | 语义澄清：任意群 @ 已可达（off-template 仅诊断），「订阅投影」描述需注明它约束的是**模板群的出站选择**而非入站可达性；attach 落地后 binding 级 chat_id 与 FR-2.6 多订阅控制面的关系要在实现单里对齐 |
| §8 名词表 | 「绑定」补 attach 方向；「绑定码」职责改写（寻址退役，仅剩项目关联判别 + G4 反查消歧的一次性短码） |
