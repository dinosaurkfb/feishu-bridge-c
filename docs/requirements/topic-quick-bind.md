# 快捷切换群与话题（Topic Quick-Bind）需求提案

- `status`: proposed（2026-09-02 Frank 口述需求，主会话整理；§4 拍板项待确认）
- 需求源：Frank 原话（2026-09-02）——第一/二层要「快捷切换群和话题」；第三层放宽为
  「飞书话题里看起来在同一个话题即可，本地是不是同一 session 不重要」。
- 触发场景：把 cc2cd 项目的 Claude 会话接进 Claude2Codex 群里 Codex 已绑定的那个话题，
  让两个智能体的产出在同一个话题里可见。

## 1. 现状与障碍（已核对代码）

1. **群**：链路模板单群（`chain-config.json` 的 `chat_id`），换群 = 改模板，无 CLI。
   FR-2.6 控制面已落盘但未接生产建话题路径。
2. **话题**：`bind-project/bind-session --apply` 只会**新建**话题；binding 的
   `root_message_id` 在建话题时产生，没有「绑定到既有话题」入口。
3. **平台限制（硬约束，1b 的死因）**：Aily 入站不提供飞书侧 root/话题 locator——对两条链
   都没建过的话题，收到 @ 也拿不到 root_message_id，出站回不进去。能绑的话题 =
   本地任一条链 registry 里有 root 记录的话题。
4. **第三层已无障碍**：Aily session 按 app 隔离（同一话题对两个 bot 是两个 session），
   Frank 放宽后这正是目标形态——同话题双 agent、各自 session、入站靠「@ 谁」消歧。

## 2. 两条实现路径

### 路径 A（方式 2）：引用既有话题直接绑定 —— 短路径，先做

- **CLI**：`bind-project.mjs` / `bind-session.mjs` 加受控参数（形态见 §4-1），语义：
  不建新话题，直接创建 binding 指向给定 root（群参数一并写入该 binding；跨群时按
  binding 级覆盖，不改机器级模板——见 §4-2）。
- **root 来源**：本地另一条链（或本链其他项目）registry 里的 binding 记录——本地可信
  记录，不依赖任何待验证 locator。
- **入站认领**：新 binding 置 pending-inbound 态，Frank 在该话题里 @ 一下本链运输 agent
  完成 session 认领——**复用现有认领机制原封不动**。
- **技能层（Frank 拍板的 UX）**：用户自然语言定位（「绑到 Codex 那个话题」），智能体从
  registry 找 root、组命令、出预览；用户只按现有习惯确认 `/feishu-bind`（授权语义不变）。
  **话题 ID 全程不过用户手**（status 不显示 locator 的纪律保持）；用户不处理权限、不执行代码。
- **出站即时可用**（有 root）；两条链的出站发布器互不感知，同话题并发发布的顺序由飞书侧
  自然序决定（无跨链协调，也不需要）。

### 路径 B（方式 1a）：pending 话题里回复即认领 —— 小改动，可并行做

- 现状：pending 话题下 Frank 的回复自动带根消息引用块，**绑定码在引用块里**，
  `findPendingBinding` 已能精确定位——卡住的只是叠加的「真实 @」闸。
- 改动：**引用块绑定码精确命中时豁免 @ 闸**（owner-only、新鲜度闸保留）。绑定码是话题
  身份的强证明（只存在于该话题根消息），安全性成立。
- 与 locator 验证无关，不等 #117 实验。

### 记录：方式 1b（任意已有话题 @ 绑定）

因 §1-3 平台限制**今天不成立**，能力域与路径 A 重合。等平台开放 locator 后再议；
届时前置还包括 chat/thread locator 验证（#117 实验的延伸）。

## 3. 安全与授权边界（沿现行纪律）

- 绑定授权照旧：`/feishu-bind` 单独成行 = 该次授权；引用式绑定同一语义（预览先行）。
- 跨链读取对方 registry：**只读** root_message_id 与群参数，不写对方任何状态。
- 同话题双 agent 的入站互扰：@ 消歧天然成立（各链 mention 闸只认自己的 transport id）；
  无 @ 消息在 Dialogue/chat 语义下的归属按各链现行判据，不新增交叉行为。

## 4. 拍板项（Frank）

1. **CLI 参数形态**：`--root-message-id <om_…>`（最直观，Frank 倾向）还是
   `--from-binding <链>:<任务/项目名>`（免 ID）？——推荐**两个都收**：前者是机器接口
   （技能层组装时用），后者是人类快捷方式；技能层默认走自然语言定位，用户两者都不用敲。
2. **跨群 binding 的群参数放哪**：binding 级记录（推荐——不动机器级模板，本项目现有
   话题不受影响；FR-2.6 的 instance_key 语义天然支持同链多群）还是改模板（全链换群，
   影响未来所有新绑定）？
3. **路径 B 的豁免范围**：仅 owner（推荐）还是 operator 也可回复认领？
